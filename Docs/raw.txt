# SkillTree IRL — Full Production Product Specification

## 0. Product Definition

**Product name:** SkillTree IRL
**Product type:** Consumer/prosumer web application with installable PWA support
**Core concept:** A persistent RPG-style representation of a person's real-world development.

SkillTree IRL converts real goals, habits, projects, learning, achievements, and activities into a persistent life progression system.

The application must not behave like a gamified todo list.

The core product model is:

**Goals change. Skills persist. History persists. The user's character continuously develops.**

A user may:

* have many unrelated goals simultaneously
* change their priorities
* pause goals
* abandon goals
* return to previous goals
* change the target of a goal
* create entirely custom goals
* track a skill without having a specific goal
* create projects with many subgoals
* track habits
* record activities that are not part of any goal
* earn achievements
* maintain years of history
* view their development as a persistent skill tree

The application must be usable by someone who wants something simple such as:

> Exercise three times per week.

And equally usable by someone managing:

* a business goal
* financial targets
* fitness
* learning
* multiple projects
* long-term personal development

The interface must progressively expose complexity rather than forcing advanced concepts on new users.

# 1. Core Product Principles

## 1.1 Permanent character, temporary objectives

The user's SkillTree profile is permanent.

Goals are temporary objectives layered on top of that profile.

Example:

A user works toward:

> Launch a software company.

During that process they earn experience in:

* software development
* databases
* design
* marketing
* sales
* business

If the business goal is later abandoned, the experience earned remains.

Never remove legitimate historical progress merely because a goal was changed, paused or abandoned.

---

## 1.2 Flexible enough for arbitrary goals

Do not hard-code the application around:

* fitness
* money
* coding
* productivity
* studying

These are templates only.

The system must support arbitrary user-defined goals.

Examples:

* restore a classic car
* read 50 books
* save £20,000
* move country
* learn Japanese
* become a better cook
* launch a company
* complete a degree
* build a house
* improve at chess
* run a marathon
* travel through Europe
* learn piano
* improve relationships
* reduce personal debt
* create an album

The goal engine must be generic.

---

## 1.3 Progress without punishment

Avoid mechanics that make users feel that previous effort has been erased.

A user who stops exercising for two weeks should not see:

> YOU FAILED.

Instead show:

* current momentum
* previous momentum
* total sessions
* lifetime XP
* personal bests
* progress history

Streaks may exist but must be secondary.

---

## 1.4 Real actions create progression

XP should represent meaningful effort.

Do not allow the product to become:

> press buttons → gain meaningless XP.

Every XP transaction should originate from:

* completing a quest
* logging an activity
* reaching a measurable milestone
* completing a habit occurrence
* unlocking an achievement
* verified external activity
* manual correction

XP must be ledger based.

to:

> Save £20,000

record a Goal Revision.

* previous target
* new target
* date
* optional reason

Display historical progress using the target that was valid at that time while displaying current progress against the new target.

1. archives or pauses the original
2. creates a new goal
3. optionally links the new goal as successor
4. carries no goal progress automatically

# 22. XP Difficulty

Default base rewards:

Tiny action: 5 XP
Small action: 10 XP
Moderate action: 25 XP
Significant action: 50 XP
Major action: 100 XP
Milestone: 150–300 XP
Major achievement: 300–1000 XP

Actual XP should account for:

* effort
* difficulty
* duration
* novelty
* recurrence
* verification
* user level

The purpose is consistency, not scientific measurement.

---

# 23. XP Diminishing Repetition

Prevent XP farming.

Repeated identical low-difficulty actions gradually reduce bonus XP.

Example:

First 5K:

Large milestone reward.

Normal future 5Ks:

Normal running activity reward.

Repeatedly completing:

> Drink water

must not become the easiest route to Level 100.

Use diminishing novelty bonus, not punitive negative XP.

---

# 24. Level Formula

Levels must require progressively more XP.

Requirements:

* first levels arrive quickly
* progression visibly slows over time
* no practical maximum level
* deterministic formula
* server authoritative

Example conceptual formula:

`required_total_xp(level) = base * level^1.65`

Exact values must be defined in shared server configuration and covered by tests.

Do not duplicate level formulas in clients.

---

# 25. Overall User Level

User receives an overall Character Level.

This is calculated from lifetime eligible XP across skills.

Avoid summing every skill's level.

Use total eligible XP.

Display:

* character level
* total XP
* XP this season
* highest skills

Character level is cosmetic and motivational.

It must not unlock essential product functionality.

* treat output as suggestions
* user confirms changes
* never let AI directly alter XP ledger
* never send sensitive private content unnecessarily
* provider abstraction
* strict cost limits
* failure fallback to deterministic templates/manual editing

AI failure must not break the app.

---

# 178. Deterministic Recommendation Engine

Provide useful recommendations without AI.

Rules based on:

* goal type
* stalled goal
* overdue quest
* nearest milestone
* user-selected focus
* previous frequency

Example:

> You haven't updated this goal for 14 days. Review it?

# 182. Core Daily Loop

The normal recurring interaction should be:

1. Open Today.
2. See current Focus goals.
3. See next useful action.
4. Complete/log real activity.
5. Receive concise progress feedback.
6. Observe relevant goal/skill movement.
7. Leave.

This should take seconds when desired.

---

# 183. Core Long-Term Loop

Weekly/monthly:

1. Review goals.
2. See what changed.
3. Adjust targets/priorities.
4. Pause irrelevant goals.
5. Create new objectives.
6. View SkillTree growth.
7. Continue.

The product should become more valuable as history grows.

# 184. Critical UX Rule

Never require the user to maintain the system more than they maintain their real goals.

If entering a 30-minute workout requires five minutes of administration, the product has failed.

Common actions need extremely short flows.

# 185. Performance UX

After user submits activity:

Do not block interface while computing every secondary achievement.

Immediate server transaction handles essential:

* activity
* progress
* XP

Secondary tasks such as:

* summary aggregation
* certain notifications

may run asynchronously.

# 187. Codex Build Instruction

Treat this specification as the source of truth.

Do not intentionally reduce this into an MVP.

Do not leave major defined workflows as placeholders.

Build the architecture so all described product behaviours coexist coherently.

Before implementing a feature, identify:

* domain model
* user workflow
* authorization
* validation
* persistence
* error handling
* loading state
* mobile behaviour
* desktop behaviour
* analytics
* testing

Do not solve defects by adding frontend-only exceptions around incorrect backend behaviour.

Fix domain logic at the authoritative layer.

Use TypeScript strict mode.

No `any` without documented justification.

Use migrations for database changes.

Keep application/domain logic separate from presentation.

Use transactions for multi-record state changes.

Test hostile authorization.

Keep all private data private by default.

Every important mutation must be safe under retries.

Every long-running process must fail gracefully.

The final product must feel like one cohesive system rather than a collection of independently implemented features.

# 188. Final Product Experience

The finished product should make a user's life appear as a continuously developing character.

At any point they can open SkillTree IRL and understand:

**What am I currently trying to achieve?**

**What should I work on next?**

**What have I accomplished?**

**What skills have I actually developed?**

**Where has my time and effort gone?**

**How have I changed during the last month, year or several years?**

A user may completely change direction without losing the value of their previous history.

Example:

2026:

Launch Business
→ paused.

2027:

Learn Cybersecurity
→ completed several milestones.

2028:

Return to Business.

Their profile might now show:

Software Development — Level 34
Cybersecurity — Level 27
Business — Level 22
Marketing — Level 14
Finance — Level 18

The person's goals changed.

Their character did not reset.

That persistent identity and progression system is the defining feature of SkillTree IRL.
